# End-to-end audit, 30 September 2026

Branch `chore/e2e-audit`. Nothing was pushed to `main` and nothing was written
to staging or production.

## Where it was run, and why not on staging

The brief was to use staging. On the day all three hosted Supabase projects
(staging `jzvqyryblsfxlinvoiuf`, production `pmjuiynjelhjlpyohbvk` and the demo)
were paused by the free tier and did not resolve in DNS, and no account on this
machine could restore them. The walkthrough was therefore run against a
throwaway local Supabase stack built from this repo's migrations, with a
production build of the app, driven by Playwright in Chrome. That proves the
code and a from-scratch deployment. It does not prove the state of the staging
or production databases, which could not be inspected.

The stack and all test data were deleted afterwards.

## Verdict

The application code works end to end, from sign-up to a final scorecard, and
the numbers match the engine and the golden benchmark. It is not ready to hand
over as a running service: the hosted environments were down, one security hole
existed in any database built from the repo (fixed on this branch, not yet
applied anywhere), and one required setup step has no screen.

## What works (each step driven in the browser at 1440x900 and 390px)

- Sign-up with e-mail confirmation, sign-in, sign-out, password reset. The old
  password is rejected after a reset. Wrong credentials and protected pages
  behave correctly.
- Company create, edit, persistence.
- Procurement assessment: create by pasting suppliers, save, reopen, edit,
  delete, report and PDF export (a valid 1.5 MB PDF). The score (25.67 of 29)
  matched a direct engine run to four decimals.
- Generic scorecard: workbook upload (22 of 22 sheets), review, import, all
  seven elements, evidence confirmation, procurement attachment, calculation,
  reopen in a new session, edit with the "calculate again" prompt, and a final
  level (Level 5, 80% recognition for the test data).
- Roles: a normal user gets a proper 403 on `/admin` and the EAP targets
  screen; an internal admin can open both.
- No console errors, failed requests or broken links across the walkthrough.
  No hydration warning on 22 pages checked in development mode.
- No secrets in the browser bundle or in tracked files.

## Fixed on this branch

1. Tenant isolation. A database built from the migrations let any signed-in
   user read, rename and delete any other user's companies and procurement
   data through the API, and let anyone read every profile (names and e-mail
   addresses). The owner-scoped policies existed only in a loose SQL file.
   They are now migration `20260930120000_strict_owner_rls.sql`. After it, the
   same attack returned zero rows and every write failed, while all owner flows
   and the admin console still worked. It must still be applied to staging and
   production, whose current policies are unknown.
2. Printable scorecard report showed "0.00 points" and "— / —" for every
   generic scorecard, because it read the older calculator's field names. It
   now shows the real total, element points and final level. Display only.
3. Phone layout. Element, result and procurement pages laid out about 500px
   wide on a 390px screen. Two layout classes fixed it; every customer-facing
   page now fits.
4. Carried over from 27 September (already approved then): the TMPS inclusion
   and exclusion sides, the dashboard tiles reading calculator scorecards, the
   demo seed storing scores, and the keep-awake job. Verified in the browser
   here: inclusions R11,000,000 minus exclusions R1,000,000, and the dashboard
   showing Avg Level and Portfolio Insights.
5. Deployment guide `docs/DEPLOYMENT.md`, README links, staging note.

## Needs a decision

1. Workforce (EAP) targets cannot be created in the app. The admin screen
   stores "black people / black women per band"; the scorecard needs the six
   population shares and rejects the other shape with a clear message. Until a
   proper screen exists the set is inserted by SQL (documented). Without it six
   Management Control indicators, 5.59 points in the golden case, cannot score.
2. A final level needs two calculations. After the last gaps are closed, the
   first calculation still reports "import awaiting review" because it reads a
   status the previous calculation wrote. A second calculation gives the final
   level. This is readiness logic, so it was left alone.
3. Preferential Procurement is capped at 25 base points in the generic
   scorecard, while the procurement module scores five base categories that add
   up to 27. The cap is deliberate and shown on the report. Someone who
   verifies scorecards should confirm which total the Codes intend.
4. The TMPS correction changes scores for any assessment that used
   "calculated TMPS". Existing saved assessments keep their old score until
   they are re-saved. Production exposure is still unmeasured.
5. Company turnover, sector and size are captured per assessment on the
   "Applicability" step, not on the company. The golden workbook's own revenue
   is R40m, which alone would classify the entity as a QSE; it scores as a
   generic entity only because applicability is set to R250m. That is the
   setting behind the earlier "wrong QSE" report.

## Too big to fix now

- The generic scorecard has no server-generated PDF. The report relies on the
  browser's "Print / Save as PDF".
- A file that is not a workbook is accepted and shown as "1 of 22 sheets" with
  "could not be read", instead of being refused outright.
- The internal admin console overflows on a phone (946px). Staff only.
- The production build bundles the whole repository, client-named documents
  included, because of a dynamic file lookup in the PDF helper.
- The legacy manual scorecard and the older full-workbook calculator load, but
  were not exercised beyond that.

## Not checked

- Staging versus production schema. Both were paused. The last recorded state
  (2 September) was that production lacked the generic scorecard tables and
  every migration from 31 July onward.
- A real Netlify deploy, Netlify's PDF path, real e-mail delivery, OAuth.
